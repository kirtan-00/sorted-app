# Scale and read-only pre-flight, 2026-09-24

Run before NSG_26 Part 1 (4,894 items) goes on the machine. The largest scan that had ever completed
here was 3,677 items, and Part 1's one previous attempt left 2,814 of 4,873 rows and all 609 segments
unembedded, on an index predating the `jobs` table so it carries no record of why it stopped.

Machine: M1, 8 GB, on battery, macOS 26.1. Encoder `ViT-B-16-SigLIP/webli`, faces and video on, 4 workers.

## The shoot

5,000 photos at 3000x2000 plus 300 ten-second clips, 6.0 GB, generated by
`scripts/make_synthetic_shoot.py`. Bursts of three near-copies every 25 frames, mtimes walking forward
so date grouping has something to group.

3000x2000 rather than a 24 MP-class 4000x3000 was a disk decision, not a measurement one: 5,000 of the
larger is 11.4 GB against 11 GB free. **Decode cost per file is therefore optimistic against a real
card.** Throughput shape, memory, database size, query latency and resume are unaffected by it.

## Does it survive 5,000 items

Yes, and it resumes from a hard kill.

| pass | ended | scanned | embedded | errors |
|---|---|---|---|---|
| 1 | SIGKILL at 90 s | 2,778 / 5,300 | 0 | 0 |
| 2 | SIGTERM at 120 s | 5,126 / 5,300 | 0 | 0 |
| 3 | completed, 397.8 s | 5,300 / 5,300 | 5,300 | 0 |

Pass 3 reported `skipped: 5126, indexed: 174` — it re-listed the shoot, recognised everything already
read, and did only the remainder. Final state `complete: true`, `unembedded: 0`, `stale_embeds: 0`,
`errors: 0`, `embed_model: ViT-B-16-SigLIP/webli`. Total wall 608.6 s across all three passes.

A SIGKILL is the honest shape of the risk: no chance to flush, no clean shutdown. It resumed anyway.
This is the specific machinery the Prod_02 index did not have.

## Does throughput degrade as the index grows

No. The features stage holds flat from row 276 to row 4,804:

```
rows ~276   31.6 items/s        rows ~3004  33.3 items/s
rows ~1376  30.9 items/s        rows ~3904  33.8 items/s
rows ~2751  32.5 items/s        rows ~4804  31.8 items/s
```

Nothing sags across the range where local experience previously ran out (3,677 items). Two apparent
slowdowns are both composition, not scaling, and neither is a defect:

- **The embed stage falls from 22.7 to 11.4 items/s.** `index.py` embeds photos, then clips, then
  segments. A clip is the mean of its sampled frames and a segment is one more encode each, so the
  last part of that stage is 300 clips and 600 segments rather than single thumbnails. 5,900 embeds
  for 5,300 items.
- **A resumed pass looks slow per item.** Pass 3's remaining 174 photos ran at 2.8 items/s, but they
  are ordinary day7 frames, no different from the 4,800 before them. Each pass pays a fixed startup —
  worker pool, face model, encoder — and over 174 items that dominates. Over 2,778 it disappears.

The operational read: **interrupts are cheap to recover from but not free.** Each resume costs roughly
a minute of startup before the first new item is processed. Stopping a scan ten times will cost ten
minutes, and none of it shows up as lost work.

Nothing measured here is worse than linear.

## Memory

Peak resident, whole run: **1,675 MB** in the parent during the embed stage, 385 MB across the feature
workers. The feature stages themselves sit at a flat 69-70 MB in the parent for their whole length,
so the 1.7 GB is the encoder and its batches, not an accumulation. On an 8 GB machine that is
comfortable but it is the number to watch if the batch size is ever raised.

## Database size and query latency

`index.db` 13.0 MB for 5,300 items with embeddings; the index folder as a whole 2,466 MB, about 465 KB
per item of thumbnails, grid images and sampled frames. **A 4,894-item card should budget roughly 2.3 GB
of index**, which is worth checking against free space before Part 1 rather than during it.

`db.scan_counts()`, which the UI runs on every render: **median 9.7 ms, max 9.9 ms** over ten
consecutive calls at full size. The 39.3 ms seen immediately after the scan finished was a cold cache
and did not reproduce.

## Read-only

`tests/test_readonly.py`. Full manifest of the shoot — every file at any depth, size, mtime to the
nanosecond, sha256 of bytes — before and after each of: a scan with faces and video on, the focus
pass, the places pass, and an export. All four leave the shoot byte-identical. The index is written
outside the shoot; `config.INDEX_DIRNAME` is a dead leftover of the abandoned index-in-place design.

That is a guarantee about this Mac's filesystem. An external card adds variables sorted does not
control: macOS writes `.Spotlight-V100`, `.fseventsd` and `._` forks to a mounted volume on its own
account. Disable Spotlight on the client drive before it is plugged in.

## What is not covered

- **E1 is not in the normal suite.** It takes 608 s and 8.3 GB. Run it by hand with
  `sorted-siglip-ab/scale_drive.py` when the pipeline changes shape. `tests/test_readonly.py` (32 s)
  is in the suite; the scan-with-faces-and-video case is 15.5 s of that.
- **Faces are synthetic-free.** The textures hold no faces, so YuNet runs on every frame but SFace
  embedding is never exercised. Real faces cost more than this run shows.
- **No RAW.** Every file is JPEG; rawpy and the Sony fallback are untested at scale.
