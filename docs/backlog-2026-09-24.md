# Backlog from the first client SSD scan, 2026-09-24

Raised while the GT 1 TB scan was running. Nothing here is implemented; the app was deliberately left
alone mid-scan. Written down so it is not re-derived later.

## 1. The error block should not shout during a scan

**What happens.** As soon as a scan has errors, the progress panel carries a red line under the bar —
*"1932 file(s) could not be read. They are skipped; tick Retry failed files and Scan again once
fixed."* — plus the full list of failed paths. It sits there for the whole scan, below a bar that is
moving normally.

**Why it is wrong now.** The message is written for a scan that has *finished*: it tells you to tick a
box and scan again, which you cannot usefully do while the current pass is still running. During the
scan it reads like a live failure, and the path list pushes the actual progress line up the page.

**What to do instead.** Split old errors from new ones, which is the distinction that matters and the
one the current panel does not make.

- **Carried over from an earlier pass:** one quiet line — *"1,932 skipped so far"* — list behind a
  disclosure. You cannot act on these until the pass ends.
- **New during this pass:** show it, loudly enough to notice. A file failing *right now* is live
  evidence the disk is playing up again, and it is the earliest warning available. On this scan the
  count moved 1,932 -> 1,933 mid-pass; under a blanket "hide errors while running" rule that single
  new failure would have been swallowed, and it was the most informative number on the screen.

When the scan ends, expand the whole thing and show the call to action then, which is the moment it
is actionable.

**The data already supports this, with no schema change.** `indexed_at` is stamped on the row when it
errors, `/api/errors` already returns it, and the jobs table carries `started`. New-this-pass is
`indexed_at >= job.started`. On this shoot the two groups separate perfectly:

```
2026-09-24 13:19:45      1     new, mid-pass
2026-09-24 12:06:50   1932     carried over from the disconnects
```

**Worth remembering:** on this scan the count was not a handful of corrupt files, it was 1,932 of
2,419 photos, all readable, all marked error because the disk dropped mid-pass. A count that large
during a scan looks like catastrophe and is actually recoverable in one retry pass. The wording
should not make a recoverable state look terminal.

## 2. Show the folder being read right now

Asked for during the same scan: the progress line says *"Scanning 392 of 644, reading photos and
clips"*, which does not say **where** it is. On a client card with a dozen top-level folders, the
useful fact is *"…/SHIVALIK FURNITURE DEALEARS MEET (06-08-2026)/FINAL JPG"*.

Shape: one dimmed line under the bar carrying the directory of the file in flight, middle-elided from
the left so the tail (the folder that identifies it) survives. Update on a timer, not per file - at
30+ files/s the text is unreadable and it is a repaint per item for nothing. The progress callback
already carries enough to derive it; `notify()` in `index_folder` is where the rel path is known.

Related, and cheap: the failed-path list in the error block is already grouped by folder in practice.
Collapsing it to *"1,904 in SHIVALIK FURNITURE DEALEARS MEET/FINAL JPG, 28 elsewhere"* would say more
than 1,932 lines of filenames.

## 3. Better video categorisation: people count, and static versus moving

Today a segment is one representative frame through the same zero-shot softmax a photo gets, with no
face rule and no duration rule (see `tests/test_segments.py`). Two axes were asked for, and both are
cheap because the frames are already on disk.

**How many people are in the frame.** YuNet already runs on stills and is never run on video frames.
Running it on the sampled frames of a clip gives a face count per frame, and per segment the median
across its frames. That splits the categories that currently collapse: a seated interview (1 face,
steady), a two-hander (2), a crowd (many). It also gives segments the thing stills have and clips
lack - the face rule - which is exactly the asymmetry that made task B necessary. Cost is one YuNet
pass over frames that are already decoded.

**Static or moving.** The sampled frames per clip are already saved as `<qhash>_<k>.jpg`. Mean absolute
difference between consecutive frames, or the distance between their existing CLIP embeddings,
separates a locked-off interview from a handheld walk-and-talk without decoding anything new. A
tripod interview and a roaming B-roll shot can carry identical category probabilities today; this is
the signal that tells them apart, and it is the one an editor actually searches on.

**Why they belong together.** "One person, static" is an interview with far more confidence than the
softmax alone can offer. "Several people, moving" is event coverage. Those two facts would likely do
more for clip categorisation than any further prompt work, and neither needs a new model.

**Before building:** re-measure on NSG_26 Part 2's 476 segments, which are pinned in
`tests/fixtures/`, so any change is compared against a known baseline rather than an impression.

## 4. Signing in to Google Drive

Not a change - it already works, it is just a six-step one-time setup, written out in
`docs/google-drive.md`. The short version:

1. <https://console.cloud.google.com/> → new project, call it `sorted`.
2. **APIs and Services → Library** → enable **Google Drive API**.
3. **OAuth consent screen** → **External**, app name `sorted`, your email in both contact fields.
   Leave it in **Testing** and add your own Google address as a **test user**. Testing mode is fine
   permanently for a one-person app.
4. **Credentials → Create credentials → OAuth client ID → Desktop app**.
5. **Download JSON**.
6. Rename it `google_client.json` and put it at
   `~/Library/Application Support/photosort/google_client.json`.

Then **Sign in to Google** on the export panel (or `photosort drive-signin`), pick the test-user
account, approve. The refresh token lands at `google_token.json`, mode 0600, and is not asked for
again unless you sign out or leave it unused six months.

Two things that catch people: uploads into a client's shared folder count against **your** Google
quota, not theirs, and the app refuses an upload that would leave under 512 MB spare - the web-size
option is the usual way out. And the full `drive` scope is needed rather than `drive.file` because a
folder someone else shared was not created by this app, so the narrow scope cannot even see it.

## 5. Ahmedabad appears twice in Places

Two piles, both named Ahmedabad:

```
23.05883, 72.56614   n=172
23.02753, 72.49382   n=64     ~8 km apart
```

`places.cluster()` is a **grid, not a radius clusterer**, whatever its docstring says:

```python
deg = km / 111.0                      # 0.225225 deg
key = (floor(lat / deg), floor(lon / deg))
```

A cell edge falls at lon `322 * 0.225225 = 72.5225`, and Ahmedabad's two piles sit either side of it.
They are 8 km apart and can never merge, because merging is not what a grid does: two points 100 m
apart land in different piles if a boundary runs between them. The docstring's "within about km of
each other" is not what the code delivers, and should be corrected whatever else is done.

The name is applied afterwards and separately: the UI calls `placeName()` -> `nearestCity()` against
the shipped `places.json`, per cluster. Two clusters, two lookups, same answer, nothing to notice the
collision.

**Fix, cheapest first.** Merge after naming rather than rewriting the clusterer: group the named
clusters by (name, country), sum `n`, union the bounding boxes so click-to-filter still selects
everything in the merged pile. Guard it with a distance cap (say 50 km) so two genuinely distinct
towns that share a name are not welded together. The grid stays, which keeps the map instant on
zoom, which is why it is a grid in the first place.

## 6. "Name this person" follows you to every tab

Seen on the Scan tab, bottom right, while a scan was running.

```js
function syncSaveForm() {
  savePersonForm.hidden = !state.findPath;
}
```

`#save-person-form` lives inside the global `#status` bar, and its visibility depends only on
`state.findPath` - whether a "find this person" is in flight. `showView()` never clears it, so once
you have searched by face the box rides along to Scan, Places, Categories, everywhere.

**Fix:** make the condition include the view (`!state.findPath || state.view !== "people"`), and call
`syncSaveForm()` from `showView()` so leaving the tab hides it. Keep `state.findPath` itself alone -
coming back to People should still offer to save the person you were naming.

## 7. What else would help an editor find footage

Asked directly: photos feel sorted, video does not. Ranked by value per unit of work, and everything
in the first two tiers needs no new model.

**Already in the index, just not surfaced.** `video.probe()` reads all of this and it is thrown away:

- **Slow motion.** fps is already probed. 100 or 120 fps is a filter editors reach for constantly,
  and right now there is no way to ask for it.
- **Camera and resolution.** make/model and width/height are already read. Grouping by body is how a
  multicam day gets cut, and how you find the one clip shot on the wrong camera.
- **Log versus Rec.709.** `pix_fmt` is read and there is already slog3 handling in the frame pass.
  "Needs grading" versus "ready to cut" is a real bucket.
- **Duration buckets.** B-roll against long takes. `INTERVIEW_MIN_DURATION_S` already leans on this
  for one narrow rule; the underlying number deserves to be a filter.

**Cheap from frames already on disk.** The sampled `<qhash>_<k>.jpg` frames are sitting there:

- **Shot size - close, medium, wide.** Falls out of YuNet for free once it runs on frames: face
  bounding box area against frame area. For an editor this is close to the most useful single axis
  there is, and it costs nothing beyond the face pass below.
- **People count** and **static versus moving** - as in section 3.
- **Exposure outliers.** A histogram per sampled frame finds the clipped and the crushed. "Show me
  what will fight me in the grade."

**Worth building, needs something new.**

- **Is anyone talking.** The app ignores audio completely today. A cheap voice-activity pass -
  energy plus zero-crossing, or webrtcvad, no model - splits interviews and pieces to camera from
  wild B-roll and room tone. For a documentary card that is the difference between 1,141 clips and
  the 200 worth opening.
- **Transcription** would beat everything else on this list for interview footage, because editors
  search for what was *said*. It is also a positioning decision, not just a technical one:
  `docs/sorted-concept.md` currently promises "No language model is used anywhere". Whisper is
  speech recognition rather than a language model, but that sentence is load-bearing in how the app
  is sold, and it should be decided deliberately rather than quietly broken.

**Order I would do them in:** fps / camera / log (a day, all metadata already read), then the face
pass over frames which buys people count and shot size together, then static-versus-moving, then
audio. Measure each against the 476 pinned segments in `tests/fixtures/` rather than by impression.

## 8. "Scanning" twice, with the counter going backwards

Watched live: the panel said *"Scanning 392 of 644, reading photos and clips"*, then a minute later
*"Scanning 448 of 3,066, learning what is in each shot"*. Same verb, counter back near the start,
total suddenly five times bigger. It reads as a restart, or a crash and recovery.

Nothing is wrong. `index_folder` emits four stages - `scan`, `features`, `faces`, `embed` - and
app.js already gives each its own words:

```js
var STAGE_TEXT = { scan: "finding files", features: "reading photos and clips",
                   faces: "finding faces", embed: "learning what is in each shot" };
var line = "Scanning " + n(done) + " of " + n(total);
```

Two things make it look broken. The headline verb is "Scanning" for every stage, so the stage label
reads as a subtitle rather than as the thing that changed. And each stage counts a different
population: `features` counted the 644 items this pass had to read, `embed` counted the 3,066 photos,
clips and segments across the whole index still missing a vector. Both numbers are right. Shown one
after the other under the same word, they look like one number that jumped.

**Fix.** Number the steps and let the stage own the verb:

```
Step 2 of 3 · reading photos and clips · 392 of 644 · 0.4/s, about 10 min left
Step 3 of 3 · learning what is in each shot · 448 of 3,066 · 17.9/s, about 2 min left
```

The step count has to be computed for the pass rather than hardcoded: `faces` only runs when faces
are on, and `scan` reports no total until it has listed the disk. Emitting `step` and `steps`
alongside `stage` in `notify()` is cleaner than having the UI guess, since index.py is the only place
that knows which stages this pass will actually run.

Worth keeping the per-stage counter rather than a single global percentage: the stages are genuinely
different work at genuinely different rates (0.4/s against 17.9/s here), and one merged bar would
crawl and then leap, which is its own kind of looks-broken.


## 9. The embed stage is three different speeds and one estimate

Watched live: embedding ran at 17.9/s, then fell to 2.55/s and looked stalled. It was not.

```
487 photos      batched via EMBED_BATCH     fast
1,140 clips     one at a time, commit each  ~7x slower
1,439 segments  batched via EMBED_BATCH     fast again
```

A clip's vector is the mean of every sampled frame, so it is roughly eight encodes rather than one,
and the loop does them a clip at a time with a commit per clip while photos and segments go through
`EMBED_BATCH`. The rate therefore drops by about 7x in the middle of a single stage and recovers at
the end. E1 predicted this on synthetic clips (22.7 -> 11.4/s); real footage makes it far starker.

Two consequences:

- **The "about N min left" estimate is computed from a blended rate and is wrong for most of the
  stage** - too optimistic during the clips, too pessimistic after them. Estimating per sub-stage,
  or at least from a trailing window rather than the whole stage, would stop it lying.
- **It looks stalled.** Same fix as item 8: name what is happening. "learning what is in each shot"
  covering all three is what makes a 7x slowdown look like a hang rather than a different kind of work.

Worth considering separately: the clip loop could batch its frames across clips instead of one clip
per call. That is a real speed-up rather than a wording change, and on this shoot it was the single
slowest part of the whole scan.

## 10. A designer rescanned a shoot for five hours because the project file was not on the disk

Samyak was handed the NSG disk, did not know a project file existed, and rescanned from scratch.
Dhrumil and two others did not, because they had been told. Being told should not be the mechanism.

**It is not a discoverability problem, or not mainly.** The welcome screen already offers two
co-equal buttons - "Scan a disk or folder" and "Open a project file", the second explained as "A
sorted_<shoot>.sorted from any Mac. The shoot opens in seconds, already sorted." If a file had been
on the disk, that button was right there.

**There was no file.** Two causes, compounding:

1. **Nothing saves it.** The panel reads "Not saved yet" until somebody presses Save project or
   command S. A scan can finish, the disk can be unplugged and handed over, and no file ever exists.
2. **For a whole-disk scan it cannot land on the disk anyway.** `bundle.default_project_dir` puts the
   file beside the shoot folder so it travels - unless the shoot's parent is `/Volumes` itself:

   ```python
   if parent.is_dir() and os.access(parent, os.W_OK) and parent.parts[-1:] != ("Volumes",):
       return parent / "sorted"
   return home / "Documents" / "sorted"
   ```

   Scan `/Volumes/GT 1 TB` and the parent is `/Volumes`, so it falls back to `~/Documents/sorted` on
   the operator's Mac - the one place that cannot travel with the disk. Scan a subfolder and it
   works. So whether handover works at all depends on how deep the folder you picked was, which
   nobody could be expected to guess.

**The tension to settle first.** Putting the file on the disk is a WRITE to a shoot disk, and the
standing rule is that a shoot disk is only ever read, with Reorganise as the single guarded
exception (`tests/test_readonly.py`). A project file beside the shoot would be a second exception.
That is a product decision, not a bug fix, and it should be made deliberately:

- **Keep read-only.** Then handover has to be explicit: when a scan finishes, ask where the project
  file should go and say plainly that without it the next person rescans. Never silent.
- **Allow this one write.** A `sorted/` folder at the top of the scanned volume, written only when
  the user asks for handover, never during a scan. `test_readonly.py` would need a carve-out as
  precise as the one Reorganise has.

**Either way, two things are true.** A finished scan should not leave "Not saved yet" sitting quietly
on a tab nobody opens - it is the one artefact that makes the next five hours unnecessary. And the
`/Volumes` fallback should say what it did: "saved to your Documents, this will NOT travel with the
disk" is a sentence that would have cost Samyak nothing and saved him a day.

## 11. Face groups load before anyone asks for them

`showView` already lazy-loads: `if (name === "people" && state.people.length === 0) loadPeople();`
But opening a shoot calls `loadPeople()` unconditionally at app.js:780, so the grouping is fetched
and rendered for every shoot whether or not the People tab is ever opened.

Drop the eager call and let the lazy one do its job. `fillPersonSelect()` is the only thing outside
the tab that depends on it - the person filter in the search bar - so that needs a cheap count
endpoint, or to populate on first open of the dropdown, rather than pulling every group up front.

## 12. The UI reads as dead

Kirtan's words: "this ui looks dead and not designed for humans". Not a list of bugs, so worth
separating what is actually being felt, from the screens seen today:

- **Nothing ever feels finished.** A scan ends and the panel keeps the same grey furniture; there is
  no moment of "done, here is your shoot, here is what to do next". The end of a scan is the single
  highest-attention moment the app gets and it currently passes in silence. Item 10 is the cost of
  that silence.
- **Everything is the same weight.** Toolbar, section headers, filters, error list and progress all
  sit at the same grey, same size, same density. With nothing louder than anything else the eye has
  nowhere to go, which is most of what "dead" means. The one warm colour in the whole product is the
  pink tile in the mark.
- **The copy is good and the hierarchy wastes it.** "Like a Premiere project: what is in each shot,
  the thumbnails, the saved people... Give it to an editor with the disk" is genuinely well written
  and it is set as a grey paragraph under a collapsed heading on a tab you only open to scan. The
  words that would have saved Samyak five hours exist; they are just not anywhere he would look.
- **Empty states carry no invitation.** "No exports yet from this shoot" states a fact and offers
  nothing.

Worth doing as one pass with a designer rather than as twelve tickets, and worth doing against a
real shoot on screen rather than an empty one - every screen looked at today had 3,560 items behind
it and that is the state the app should be designed in.

## 13. How an editor actually searches, and what selecting and exporting should feel like

Today a clip lands in exactly one category and the UI shows one grid. An editor does not think in one
category. They think in several constraints at once - *"wide shots, outside, no faces, from the
6 Aug day, usable"* - and they think in **stacks**: pull everything that might work, then whittle.

**Show every category a clip belongs to, not just the winner.** `_score` already computes the full
probability distribution over every category and throws all but the top one away. A clip that is
0.41 interview and 0.38 people is filed as interview and becomes invisible to someone browsing
people, even though it is genuinely both. Keeping the runners-up above a threshold costs nothing -
the numbers already exist - and turns a single-bucket tree into something an editor can actually
browse. The same clip appearing under `interview`, `office` and `2 people` is correct, not a bug.

**Filters should combine, and say what they cost.** Every facet worth having is a fact already in the
index or one pass away: day, place, category, people count, shot size, static or moving, slow motion,
camera, duration, usable. The useful move is combining them with a live count as you go - *"wide +
outside + no faces = 34 clips"* - so an editor learns the shoot by narrowing it rather than by
scrolling it.

**Selection is the real workflow and it is currently the weakest part.** An editor does not find and
export once. They find, add to a pile, search again, add more, remove a few, then send the pile. That
needs a selection that survives changing the search, a visible running count and size, and a way to
see the pile on its own before sending it.

**Colour is the fastest thing to reach for.** Editors already live in colour labels - Premiere and
Resolve both do it, and everyone who cuts has the habit. It should mean something chosen by the
editor, not by us: a swatch on a clip, filterable, carried into the export folder name or an
accompanying CSV, and round-tripping into Premiere as a label would make the handover feel native.
Note this is the one place a warm accent belongs in a UI whose only current colour is the pink tile
in the mark (item 12).

**Export should show what is about to happen before it happens.** How many files, how big, where they
land, and for a web-size export roughly how long. The current panel asks for a folder name and a
size and then goes. A one-line summary above the button - *"34 clips, 12.4 GB, to /Volumes/... as
2048px JPEG, about 6 minutes"* - is the difference between confidence and a held breath.

**Order I would build it:** multi-category first, because the data is already computed and thrown
away and it changes browsing immediately; then combining filters with live counts; then a persistent
selection; then colour labels; then the export summary.
